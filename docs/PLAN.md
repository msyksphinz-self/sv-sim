# sv-sim 開発計画 (ドラフト v0.1)

Rust で一から書く SystemVerilog シミュレータ。

## 0. 目標と非目標

### 目標
| 項目 | 方針 |
|---|---|
| 言語 | IEEE 1800-2023 のフルサポートを最終目標 (設計記述 + 検証機能: class / randomize / coverage / SVA / UVM) |
| 値 | 4 値 (0/1/X/Z) を正しく扱う。ネットの強度 (strength) と解決関数も含む |
| inout | 多重ドライバ、`tri`/`wand`/`wor`/`tri0`/`tri1`/`trireg`/`supply*`、`pullup`/`pulldown`、`tran`/`tranif*`/`rtran*` 双方向スイッチまで正しく動かす |
| 速度 | イベントドリブンの意味論を守りつつ、ネイティブコード生成 (JIT) と静的スケジューリングで Verilator 級を狙う |
| AI アシスト | シミュレータ自体を AI エージェントから操作・問い合わせできる設計 (後述 §7) |
| 実装 | Rust (stable)、Cargo workspace |

### 非目標 (少なくとも初期は)
- 合成 / 等価性検証
- アナログ / AMS
- GUI 波形ビューア (VCD/FST を出して既存ビューアを使う)

> 現実的な注意: 「フル SystemVerilog」は商用ツールでも数十人年規模。
> 段階的に、**各マイルストーンで実際に使えるもの**を出すロードマップにする。

## 1. 全体アーキテクチャ

```

    │
 [preproc]   `define / `ifdef / `include / `timescale, マクロ展開 (ソース位置を保持)
    │
 [syntax]    lexer → 手書き再帰下降パーサ (式は Pratt) → ロスレス CST
    │
 [sema]      名前解決、型システム、定数評価、パッケージ/インポート
    │
 [elab]      パラメータ確定、generate 展開、階層構築、interface/modport 接続、
    │        bind、defparam、configuration
    │
 [mir]       シミュレーション用中間表現 (SSA 風、プロセス = 再開可能な状態機械)
    │        最適化: 定数畳込み、2値推論、組合せ回路の levelization、ネット統合
    │
 ├─[interp]  バイトコードインタプリタ (最初の実装・リファレンス・デバッグ用)
 └─[jit]     Cranelift による JIT ネイティブコード生成 (高速モード)
    │
 [runtime]   IEEE 1800 §4 の層別イベントキュー、ネット解決、スイッチネットワーク、
             タイミング、$system tasks、DPI-C、VPI、波形出力
```

## 2. フロントエンド

- **パーサは手書き**。理由: (1) 速度、(2) エラー回復と分かりやすい診断 (AI アシストに直結)、
  (3) SV の文法は曖昧箇所が多く (`a[b]` の型/式、`#` の多義性など) ジェネレータより制御しやすい。
- CST はロスレス (rowan 風: trivia/コメント保持)。将来 LSP / フォーマッタ / AI のコード修正提案に使える。
- 既存の `sv-parser` crate や slang (C++) は**比較用オラクル**として利用 (テストで AST の差分比較)。
- プリプロセッサはマクロ展開の「展開元位置」を全トークンに保持し、エラー表示で展開チェーンを出す。
- 大規模設計向けにファイル単位で並列パース (rayon)。

## 3. 4 値ロジック表現 (`svsim-logic`)

- VPI と同じ **aval/bval の 2 プレーン表現**:
  `(a,b) = (0,0)→0, (1,0)→1, (0,1)→Z, (1,1)→X`
  - 64bit ワード単位でビット並列演算。AND/OR/XOR/加算などはワード単位の論理式で X 伝播を計算。
- 幅 ≤ 64 はインライン (アロケーションなし)、それ以上はワード配列 (SmallVec / arena)。
- **2 値高速パス**: `bit`/`int` 型、および静的解析で X/Z が来ないと証明できた信号は bval プレーンを省略。
- 符号付き/符号なし、幅拡張、自己決定/文脈決定の幅規則 (§11.6/11.8) を型レベルで正しく実装。
- real/shortreal/string/chandle は別型。
- この crate は proptest + 参照モデル (素朴な 1 ビットずつの実装) との差分テストで徹底検証する。

## 4. ネット・強度・inout (`svsim-runtime::net`)

inout を「ちゃんと動かす」ための設計:

1. **ドライバの分離**: 各ネットは「ドライバ集合」を持ち、ネットの値は常に解決関数の出力として計算。
   `assign`、ポート接続 (inout の両方向)、ゲート出力、`pullup` 等すべてがドライバ。
2. **強度付き値**: 1 ビットあたり (値, 0側強度, 1側強度) を持つ表現 (§28.12 の曖昧強度にも対応)。
   強度が絡まないネット (単一ドライバ、デフォルト強度) は**通常の 4 値表現に縮退**させて高速化。
3. **解決関数**: `wire/tri`, `wand/triand`, `wor/trior`, `tri0/tri1`, `trireg`(電荷保持・減衰), `supply0/1`、
   ユーザ定義 nettype (`nettype` + resolve 関数, §6.6.7) も対応。
4. **ポート接続**: inout ポートはポートコラプス (上位/下位ネットを同一ネットに統合) を基本とし、
   型が違う / 強度変換が必要な場合のみ分離して双方向接続。
5. **双方向スイッチ (`tran` 系)**: スイッチで繋がったネット群を連結成分として求め、
   値変化時に成分全体を強度ベースで反復解決 (switch-level simulation)。`tranif` の制御変化で成分を動的に再計算。
6. **ドライバ単位の診断**: 「このネットが X なのは誰と誰が衝突しているから」を即答できるようドライバ情報を保持
   (AI アシストの因果追跡に利用)。

## 5. 実行モデルとスケジューラ

- IEEE 1800 §4 の層別イベントキューを忠実に実装:
  Preponed → Active → Inactive → NBA → Observed → Reactive → Re-Inactive → Re-NBA → Postponed
  (+ PLI 用リージョン)。
- **時間ホイール** (近い未来はバケット、遠い未来はヒープ) で `#delay` を管理。
- **プロセス = 再開可能な状態機械**: `always`/`initial`/`fork` 子プロセス/タスクの `@`/`#`/`wait` を
  MIR 段階でサスペンドポイントに分割 (Rust の async 変換に近い)。スタックフルが必要なケース
  (再帰タスク内での待ち等) はヒープフレームで対応。
- **感度リスト**: 信号ごとに待機プロセスのリスト。値変化時のみ起床 (エッジ検出含む)。

## 6. 高速化戦略

速度は段階的に積み上げる。正しさはインタプリタを常にリファレンスとして差分テスト。

1. **静的スケジューリング**: `assign` / `always_comb` / 組合せ `always @*` の網を依存グラフ化し、
   トポロジカル順に並べた関数に融合 (Verilator 方式)。ループがある / 遅延がある部分だけイベント駆動に残す。
   → イベントキューのオーバーヘッドを大部分削減しつつ、意味論は保持。
2. **2 値推論**: X/Z が入り得ない信号を検出して 2 値表現に (4 値サポートは維持しつつ速度を回収)。
3. **JIT (Cranelift)**: MIR → Cranelift IR → ネイティブ。コンパイル時間が短く、
   「起動が速い + 実行も速い」を両立。将来 LLVM バックエンドで AOT 最適化も選択肢。
4. **データ配置**: 信号値を連続メモリ (SoA) に配置し、キャッシュ効率を最大化。ホットループでアロケーションしない。
5. **マルチスレッド** (後期): 静的スケジュール部分をパーティション分割して並列評価。
6. **ベンチマーク基盤を初期から用意**: Icarus / Verilator と同一設計で比較 (CI で回帰検出)。

## 7. AI アシスト

「シミュレータに AI を埋め込む」のではなく、**AI エージェントが一級市民として操作できるシミュレータ**にする。
LLM 呼び出しは任意のプラグイン層に閉じ込め、コアは決定的に保つ。

| 機能 | 内容 |
|---|---|
| 構造化診断 | 全エラー/警告を JSON でも出力 (位置、原因、修正候補 fix-it 付き)。LLM が直接修正可能 |
| MCP サーバ | `svsim mcp` でシミュレーションをセッションとして公開: 実行/停止/ブレーク、任意時刻の信号値取得、階層探索、波形区間の要約 |
| 因果追跡 ("why") | 「`top.u_core.valid` が時刻 1200ns に X なのはなぜ?」→ ドライバ・代入文・入力値を遡ったグラフを返す。AI が根本原因を説明する材料 |
| 波形要約 | 長い波形を「状態遷移列」「プロトコルトランザクション」に圧縮して LLM のコンテキストに入る形にする |
| アサーション失敗の説明 | SVA 失敗時に、どのサイクルのどの部分式で失敗したかの構造化トレース |
| (後期) 自然言語 → テスト | 仕様文から SVA / テストベンチ雛形を生成 (LLM プラグイン) |

## 8. マイルストーン

各マイルストーンの完了条件 = テストスイートの合格率 + 動くデモ。

| M | 内容 | 完了条件 |
|---|---|---|
| **M0** 基盤 | workspace、`svsim-logic` (4 値演算完全版)、診断基盤、CI | logic の差分テスト・proptest 全通過 |
| **M1** Verilog コア | プリプロセッサ、Verilog-2005 の主要構文、module/port、`assign`/`always`/`initial`、ブロッキング/ノンブロッキング、`#`/`@`、`$display`/`$finish`/`$time`、VCD、インタプリタ | カウンタ・FIFO 等が動き Icarus と出力一致 |
| **M2** ネットと inout | 多重ドライバ、強度、全ネット種別、`tran` 系、ゲート/UDP、generate、parameter、function/task、specify は解析のみ | 双方向バス (I2C 風 open-drain 等) テスト、ivtest の該当部分合格 |
| **M3** SV 設計記述 | `logic`、`always_ff/comb/latch`、struct/union/enum/typedef、packed/unpacked 多次元配列、package、interface/modport、`unique`/`priority`、streaming 演算子 | sv-tests の設計系チャプター大半合格、実在 OSS コア (例: 小型 RISC-V) が動く |
| **M4** 高速化 | MIR 最適化、静的スケジューリング、2 値推論、Cranelift JIT | 同コアで Icarus 比 ≫ 10 倍、Verilator に近い性能 |
| **M5** 検証言語 I | class (継承・virtual・parameterized)、string、動的配列/キュー/連想配列、fork/join 系、event、mailbox/semaphore、program、clocking block | クラスベースの簡易テストベンチが動く |
| **M6** 検証言語 II | `randomize` + 制約ソルバ、covergroup、SVA (immediate/concurrent、sequence/property)、DPI-C | 制約・カバレッジ・アサーションのテスト合格 |
| **M7** UVM | UVM (IEEE 1800.2) ライブラリを無改造で実行、VPI | UVM のサンプル環境が動作 |
| **M8** スケール | マルチスレッド、FST、インクリメンタルコンパイル、セーブ/リストア | 大規模 SoC 規模で実用速度 |

AI アシストは各段階で並行追加: M1 で構造化診断、M2 で因果追跡の基礎データ、M3 で MCP サーバ、以降拡充。

## 9. テスト戦略

- **sv-tests** (CHIPS Alliance) — 規格チャプター別の網羅テスト。合格率をダッシュボード化。
- **ivtest** (Icarus のテストスイート) — Verilog 部分の回帰。
- **差分テスト**: 同じ設計を Icarus / Verilator / (可能なら) 商用ツールで流し、`$display` 出力と VCD を比較。
- **インタプリタ vs JIT** の差分テスト (fuzz 生成した設計で)。
- 式のランダム生成 fuzzing (幅規則・符号・X 伝播のバグ検出)。
- 性能ベンチマークを CI で継続計測。

## 10. 主なリスクと対策

| リスク | 対策 |
|---|---|
| 規格の巨大さ | sv-tests 合格率でスコープを可視化し、使われる機能から優先 |
| 4 値・強度で遅くなる | 縮退表現 (強度なし→4 値→2 値) を静的解析で選択 |
| イベント意味論と静的スケジューリングの両立 | インタプリタ (純イベント駆動) を正解とした差分テストで担保 |
| 制約ソルバの難しさ | まず BDD/区間伝播ベースで実装、難しい制約は SAT (varisat 等) へフォールバック |
| UVM が要求する機能の広さ | M5–M6 で UVM が使う機能リストを先に洗い出して優先付け |

## 11. 未決事項 (要相談)

1. **AI アシストの優先度と形**: MCP サーバ経由で外部エージェント (Claude Code 等) から使う形で良いか。
   シミュレータ内蔵で LLM API を直接叩く機能も欲しいか。
2. **最初のターゲット設計**: 動かしたい具体的な RTL / テストベンチがあれば、それを M3 のゴールにする。
3. **速度の比較対象**: Verilator 並みを目指すか、「4 値のまま商用イベント駆動シミュレータより速い」を目指すか。
4. **ライセンス**: (例: Apache-2.0 / MIT デュアル)
5. **ユーザ定義プリミティブ (UDP) / specify / SDF タイミング** の優先度 (ゲートレベルシミュレーションが必要か)。
