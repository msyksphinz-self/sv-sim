# sv-sim 開発計画 (ドラフト v0.2)

Rust で一から書く SystemVerilog シミュレータ。

## 0. 目標と非目標

### 目標
| 項目 | 方針 |
|---|---|
| 言語 | IEEE 1800-2023 のフルサポートを最終目標 (設計記述 + 検証機能: class / randomize / coverage / SVA / UVM) |
| 値 | 4 値 (0/1/X/Z) を正しく扱う。ネットの強度 (strength) と解決関数も含む |
| inout | 多重ドライバ、`tri`/`wand`/`wor`/`tri0`/`tri1`/`trireg`/`supply*`、`pullup`/`pulldown`、`tran`/`tranif*` 双方向スイッチまで正しく動かす |
| DPI-C | `svdpi.h` 互換 ABI。import/export、context/pure、open array、時間を消費する export task まで |
| 速度 | JIT ネイティブコード + 静的スケジューリング + **マルチコア並列** (§7) |
| デバッグ / AI | **波形ダンプ不要のデバッグ**: テスト失敗後に任意の信号・任意の時刻の値をオンデマンド取得 (§8)。波形ビューアおよび AI エージェントと結合 |
| 対象 RTL | 公開されている標準的な SV コードを片っ端から収集して回帰テスト (§10)。最終目標は業務の大型 SoC |
| 実装 | Rust (stable)、Cargo workspace |

### 非目標
- ゲートレベルシミュレーション (UDP の評価、`specify` のタイミング、SDF back-annotation)。
  ただし構文は読めるようにし、`specify` ブロックは無視する (RTL に混ざっていても落ちないように)。
- 合成 / 等価性検証、アナログ / AMS
- 独自 GUI 波形ビューア (既存ビューアと結合する)

> 「フル SystemVerilog」は商用ツールでも数十人年規模。
> 段階的に、**各マイルストーンで実際に使えるもの**を出すロードマップにする。

## 1. 全体アーキテクチャ

```
 .sv files / filelist (-f, +incdir, +define, -y/-v)
    │
 [preproc]   `define / `ifdef / `include / `timescale、マクロ展開 (ソース位置を保持)
 [syntax]    lexer → 手書き再帰下降パーサ (式は Pratt) → ロスレス CST     ← ファイル単位で並列
 [sema]      名前解決、型システム、定数評価、package/import
 [elab]      パラメータ確定、generate 展開、階層構築、interface/modport、bind、defparam、config
 [mir]       シミュレーション用中間表現。プロセス = 再開可能な状態機械
    │        最適化: 定数畳込み、2 値推論、組合せ回路の levelization、ネット統合
    │        ★ パーティション分割 (§7)
 ├─[interp]  バイトコードインタプリタ (リファレンス実装)
 └─[jit]     Cranelift JIT (高速モード)
    │
 [runtime]   層別イベントキュー、ネット解決、スイッチネットワーク、システムタスク、
             DPI-C、VPI、並列実行エンジン、チェックポイント/リプレイ
    │
 [debug]     デバッグサーバ: 波形ビューア / MCP (AI) / CLI からのオンデマンド問い合わせ
```

### 横断的な設計原則 (初期から守る)
1. **全シミュレーション状態はフラットなアリーナに置く**。
   信号値・変数・プロセスの再開位置・イベントキューを連続メモリで管理する。
   これでスナップショットは memcpy で済み、パーティションごとのメモリ分離も JIT からのアクセスも単純になる。
2. **決定性**: 同じ入力 (ソース、plusargs、seed) なら、スレッド数に関係なく同じ結果を出す。
   並列化とリプレイ型デバッグの両方の前提になる。
3. **デバッグ情報の保持**: MIR やネイティブコードまで、元のソース位置とドライバ情報を対応付けて保持する。

## 2. フロントエンド

- **パーサは手書き**。速度、エラー回復、分かりやすい診断のため。
- CST はロスレス (コメント保持)。将来 LSP や AI による修正提案に使える。
- `sv-parser` crate / slang は**比較用オラクル**として使う。
- マクロ展開の展開元位置を全トークンに保持する。
- 大規模 SoC 向け: ファイル単位の並列パース、パース/エラボ結果のキャッシュ (インクリメンタルコンパイル)。
- 業務コードを想定し、ツール固有の拡張・寛容モードも用意する (例: VCS が通すが規格違反のコード)。

## 3. 4 値ロジック表現 (`svsim-logic`)

- VPI/DPI と同じ **aval/bval の 2 プレーン表現** `(a,b)=(0,0)→0,(1,0)→1,(0,1)→Z,(1,1)→X`。
  → DPI の `svLogicVecVal` とメモリ表現が一致するので、DPI 呼び出し時の変換コストが小さい。
- 64bit ワード単位のビット並列演算。幅 ≤ 64 はインライン。
- **2 値高速パス**: `bit`/`int` 型と、静的解析で X/Z が来ないと証明できた信号。
- 幅規則・符号規則 (§11.6/11.8) を正確に実装する。参照モデルとの差分テストと proptest で徹底検証する。

## 4. ネット・強度・inout

1. 各ネットはドライバ集合を持ち、値は常に解決関数の出力として計算する (inout の両方向ドライバを含む)。
2. 強度付き値 (値 + 0 側/1 側強度、曖昧強度対応)。強度が絡まないネットは通常の 4 値表現に縮退させる。
3. 解決関数: `wire/tri`、`wand`、`wor`、`tri0/1`、`trireg`、`supply0/1`、ユーザ定義 `nettype`。
4. inout ポートはポートコラプス (同一ネットに統合) が基本。型変換や強度変換が要る場合だけ分離する。
5. `tran` 系スイッチは連結成分単位で強度解決する。`tranif` の制御が変化したら成分を再計算する。
6. 「X の原因はどのドライバの衝突か」を即答できるようにドライバ情報を保持する (§8 の因果追跡で使う)。

## 5. 実行モデルとスケジューラ

- IEEE 1800 §4 の層別イベントキューを忠実に実装する (Preponed … Active / Inactive / NBA / Observed / Reactive / Re-NBA … Postponed)。
- 時間ホイール (近い未来はバケット、遠い未来はヒープ)。
- プロセスは MIR 段階でサスペンドポイントごとに状態機械へ分割する。スタックフルが必要なケースはヒープフレームを使う。

## 6. DPI-C (`svsim-dpi`)

- **ABI 互換**: 標準の `svdpi.h` を同梱する。ユーザの C/C++ を変更なしでビルドしてリンクできるようにする。
  - `svBit`/`svLogic`/`svBitVecVal`/`svLogicVecVal`/`svOpenArrayHandle`/`svScope` を規格どおりに。
  - 引数の受け渡し規則 (input は値または const ポインタ、output/inout はポインタ、packed 型はベクタ) を Annex H どおりに。
- **ロード方法**: `-sv_lib foo` / `-sv_liblist` で `.so` を `dlopen` する。C ソースを渡されたら `cc` を呼んでビルドする補助も付ける。
- **import**: function/task、`pure`、`context`、open array (`[]`)、`chandle`、`string`。
  JIT コードからは C 関数を直接呼び出す (Cranelift でネイティブ呼び出し規約を生成)。
- **export**: SV の function/task を C から呼べるシンボルとして公開する。
  - **時間を消費する export task** (C → SV task が `#10` で待つ) は、C のスタックをまたいでプロセスを中断する必要がある。
    DPI 呼び出しを含むプロセスは**専用スタックを持つスタックフルコルーチン**で実行する (corosensei 等)。
  - `svGetScope`/`svSetScope`/`svPutUserData` などのスコープ API。
- **並列実行との関係** (§7): DPI 関数はスレッド安全とは限らない。デフォルトでは DPI 呼び出しを
  **1 本のスレッドに直列化**する (あるいはそのプロセスを含むパーティションを固定スレッドに置く)。
  `pure` やユーザ指定 (`--dpi-thread-safe=func`) のものは並列に呼んでよい。
- **チェックポイントとの関係** (§8): C 側の状態はアリーナ外にあるので、DPI を使う設計では
  fork ベースのスナップショット、または DPI 呼び出しの記録/再生で対応する。
- VPI (`vpi_user.h`) も同じ crate で提供する (cocotb 等を動かす目的)。

## 7. マルチコア並列

「独立している、または関係の薄いモジュールを別コアで同時にシミュレーションする」を正面から設計に入れる。

### 7.1 並列化の 3 つの粒度
| 粒度 | 内容 | 効く場面 |
|---|---|---|
| **A. パーティション並列** (主軸) | 設計をモジュール/サブ階層単位のパーティションに分け、各パーティションを専用スレッドで実行。境界信号だけで通信 | SoC のサブシステム (CPU クラスタ、各ペリフェラル、DDR コントローラ等) |
| **B. 評価並列** | 1 タイムステップ内の静的スケジュール済み組合せ/順序回路の評価を、依存グラフのタスクに分けて並列実行 (Verilator の mtask 方式) | 巨大な単一モジュール、密結合な回路 |
| **C. ジョブ並列** | 回帰テストの複数テスト/seed を同時実行。コンパイル結果を共有 | 回帰 (実装は容易だが効果大) |

### 7.2 パーティション並列の同期方式
- 基本は**保守的同期**。各パーティションは同じデルタサイクルを並列に進め、デルタの境界で
  バリア同期して境界信号を交換する。境界信号はダブルバッファにする。
- **ルックアヘッドで同期回数を減らす**のが速度の鍵。
  - 境界信号がフリップフロップ出力 (`always_ff` の NBA で更新される) なら、
    そのタイムステップ内で相手に影響するのは NBA 後だけなので、Active 領域のデルタごとに同期する必要はない
    → **タイムステップあたり 1〜2 回の同期で済む**。業務 SoC のサブシステム境界はほぼこの形 (レジスタ境界、バス I/F)。
  - クロックドメインが違うパーティションは、互いのクロックエッジ時刻を見込んで同期する。
  - 境界を `#delay` 付きで駆動している場合は、その遅延分だけ先に進める (古典的な PDES のルックアヘッド)。
- 境界信号の変化が稀な場合 (割り込み線、低速 I/F など) は「変化があったときだけ通知」で同期をさらに省く。
- 楽観的同期 (Time Warp: 先に進めて矛盾したら巻き戻す) は複雑なので当面やらない。
  ただしチェックポイント基盤 (§8) があるので、将来の選択肢としては残る。

### 7.3 パーティションの決め方
- **自動分割**: エラボレーション後の階層とネット接続をグラフにし、次のコストモデルで分割する。
  (評価コストの見積もり、または前回実行のプロファイル) × (境界信号数) × (境界がレジスタ境界か)。
  グラフ分割アルゴリズム (METIS 風の多レベル分割) を使う。
- **ユーザ指定**: 設定ファイルで `partition cpu_cluster = top.u_soc.u_cpu*;` のように指定する。
  業務 SoC ではこれが一番確実。
- **テストベンチ** (class、UVM、mailbox、DPI) は意味論上逐次的なので 1 つのパーティションにまとめ、
  並列化の対象は主に DUT 側にする。
- 分割結果と、同期回数・待ち時間のプロファイルを出力し、分割をチューニングできるようにする (AI に提案させる用途にも使える)。

### 7.4 実装上の注意
- ワーカースレッドは固定数でコアに pin する。同期はスピンとパークのハイブリッドバリアにする (rayon はデルタ粒度では重い)。
- パーティションごとに状態アリーナを分け、false sharing を避ける。NUMA も考慮する。
- 決定性: 境界信号の交換順とイベント処理順を固定し、スレッド数が変わっても結果を変えない。
- `$display` などの出力はパーティションごとにバッファし、時刻とパーティション ID で整列して出力する。

## 8. 波形レスデバッグ (AI / ビューア結合)

目標: **事前に波形をダンプしない**。テストが落ちたあとで、見たい信号・見たい時刻の値を
その場で取得できるようにする。人間は波形ビューアから、AI は MCP から、同じ仕組みを使う。

### 8.1 基本方式: チェックポイント + 決定的再実行
```
本番実行 (高速、波形なし)
  └─ 定期的にスナップショットを取る (例: N サイクル / 一定シミュレーション時間ごと、間隔は適応的に調整)
       ※ 状態は全部アリーナにあるので、スナップショットは差分 memcpy で済む (§1 原則 1)
テスト失敗 / ユーザ要求
  └─ 「信号 S を時刻 [t0, t1] で」という問い合わせ
       └─ t0 直前のスナップショットから復元
            └─ S (と、その計算に必要なもの) だけにプローブを付けて再実行し、値を返す
```
- 再実行は区間が短いので速い。問い合わせのたびに必要な信号だけ記録するので、ダンプ量はほぼゼロ。
- **決定性** (§1 原則 2) が前提。乱数 seed、`$random`、plusargs は自動的に保存する。
- **DPI の副作用**: DPI import の戻り値と出力引数を本番実行中に記録しておき、再実行時は C を呼ばずに再生する
  (rr 的な手法)。C 側の内部状態ごと必要な場合は fork ベースのスナップショット (OS のコピーオンライト) に切り替える。
- スナップショットはディスクにも保存できるようにし、**シミュレーション終了後もデバッグセッションを再開**できるようにする
  (例: `svsim debug run.svdb`)。

### 8.2 補助: 軽量な常時記録 (オプション)
- 順序素子 (FF の値) の変化だけを圧縮して常時記録するモードを用意する。
  組合せ信号の値はその場で再計算できるので、再実行なしに即答できる範囲が広がる。
- 「最後の M サイクル分は全信号をリングバッファに保持」するモードも用意する
  (アサーション失敗直前の様子がすぐ見られる)。

### 8.3 問い合わせ API (`svsim-debug`)
| API | 内容 |
|---|---|
| `value(sig, t)` / `values(sig, t0..t1)` | 信号の値と変化点列 |
| `find(expr, t0..t1)` | 条件式が成立する時刻を探索 (例: `valid && !ready` が最初に成立する時刻) |
| `why(sig, t)` | 因果追跡。その値を作った代入文・ドライバ・入力値を遡ったグラフを返す。X の発生源の特定など |
| `drivers(sig)` / `loads(sig)` | 静的な接続情報 |
| `scope(path)` | 階層の探索、信号一覧 |
| `transactions(if, t0..t1)` | バスやハンドシェイクを「トランザクション列」に要約 (AI のコンテキストに収まる形) |
| `assertion_trace(id)` | SVA 失敗時にどのサイクルのどの部分式で落ちたか |
| `eval(expr, t)` | 任意の SV 式をその時刻の状態で評価 |

### 8.4 フロントエンド
- **波形ビューア結合**: Surfer (Rust 製の波形ビューア) の **WCP (Waveform Control Protocol)** に対応する。
  ビューアで信号を追加した瞬間にシミュレータ側が再実行して値を返す「仮想波形」にする。
  ビューアは事前ダンプされたファイルを読むのと同じ感覚で使える。
  互換性のため、オンデマンドで FST/VCD を切り出して出力する機能も付ける。
- **MCP サーバ** (`svsim-mcp`): 上記 API を AI エージェント向けに公開する。想定する流れは次のとおり。
  「テスト X が落ちた → エラーメッセージの時刻付近の関連信号を `values` で取得 → `why` で遡る →
  根本原因の候補と、それを裏付ける信号値を提示する」。
- **CLI / REPL**: `svsim debug` で対話的に問い合わせる (gdb 風)。
- 構造化診断 (JSON、fix-it 付き) はコンパイルエラー側の AI 支援として引き続き提供する。

## 9. 高速化 (単一スレッド)

1. 静的スケジューリング: 組合せ網を依存順の関数に融合する。ループや遅延がある部分だけイベント駆動で残す。
2. 2 値推論。
3. Cranelift JIT (将来は LLVM による AOT も)。
4. SoA のデータ配置、ホットループでアロケーションしない。
5. チェックポイントのコストを小さく保つ (差分スナップショット、間隔の自動調整)。目標はオーバーヘッド数 % 以内。
6. ベンチマークを CI に入れ、Icarus / Verilator と継続比較する。

## 10. テストコーパス戦略

「標準的な SV コードを片っ端から拾ってきてテストする」を仕組み化する。

### 10.1 コーパスマネージャ (`corpus/`)
- マニフェスト (TOML) に、リポジトリ URL、固定コミット、filelist、top、define、期待結果の取り方を書く。
- **ソースは vendoring しない** (ライセンスのため)。テスト時に取得してキャッシュする。
- 各エントリを段階的に評価する: `preprocess → parse → elaborate → simulate → 比較`。
  どこまで通ったかをダッシュボード化し、失敗はエラー種別ごとに自動分類する (どの未実装機能を優先すべきかが見える)。
- 期待値: Verilator / Icarus で同じテストを実行した `$display` 出力・終了ステータス・指定信号の値と比較する。
  リポジトリ自身がセルフチェック付きテスト (PASS/FAIL を出す) を持っていればそれを使う。

### 10.2 収集候補 (例)
| 種別 | 候補 |
|---|---|
| 規格網羅 | sv-tests (CHIPS Alliance)、ivtest (Icarus)、Verilator の test_regress (使える部分)、slang のテスト |
| CPU コア | ibex、CVA6、picorv32、SERV、VexRiscv (生成 Verilog)、BlackParrot、cv32e40p |
| IP 群 | PULP common_cells / axi / register_interface、OpenTitan の各 IP、darkriscv、各種 UART/SPI/I2C/Ethernet |
| SoC | OpenTitan (Earl Grey)、Chipyard 生成 Verilog、OpenPiton、Caravel |
| 検証 | UVM 公式サンプル、OpenTitan DV (UVM + DPI を多用するので DPI のテストにも最適)、cocotb のサンプル (VPI) |
| inout | I2C/1-Wire など open-drain 系、パッドモデル、OpenTitan の pinmux/pad |

### 10.3 業務大型 SoC への道筋
- コマンドラインを VCS/Xcelium/Questa の主要オプション (`-f`、`+incdir+`、`+define+`、`-y`/`-v`、`+libext+`、
  `-timescale`、`+plusargs`) と互換にし、既存の filelist をそのまま使えるようにする。
- コンパイル時間・メモリ使用量を最初から計測し、数百万行規模で破綻しないようにする (並列パース、インクリメンタルコンパイル)。
- **リスク: 暗号化 IP** (`` `pragma protect `` で暗号化されたベンダ IP) は復号できない。
  業務 SoC には含まれることが多いので、その部分の扱い (ベンダ提供の平文モデルを使う、
  ブラックボックス化して DPI モデルに置き換える、など) を早めに確認する必要がある。
- 社外に出せないコードでも回せるよう、コーパスマネージャはローカルのプライベートなマニフェストも扱えるようにする。

## 11. マイルストーン

| M | 内容 | 完了条件 |
|---|---|---|
| **M0** 基盤 | workspace、`svsim-logic`、診断、アリーナ型状態管理、CI、コーパスマネージャの雛形 | logic の差分テスト合格、sv-tests のパース段階を計測開始 |
| **M1** Verilog コア | プリプロセッサ、Verilog-2005 主要構文、イベントキュー、インタプリタ、`$display` 等 | 簡単な設計で Icarus と出力一致 |
| **M2** ネットと inout | 多重ドライバ、強度、全ネット種別、`tran`、generate、parameter、function/task | open-drain バス等の inout テストに合格、ivtest の該当部分に合格 |
| **M3** SV 設計記述 + DPI 基本 | `logic`、`always_*`、struct/enum/union、packed/unpacked 配列、package、interface/modport、**DPI-C import** | ibex / picorv32 等が動く |
| **M4** 波形レスデバッグ v1 | チェックポイント、再実行、問い合わせ API、CLI、MCP、WCP (Surfer) 連携 | 失敗テストに対しダンプなしで任意信号を取得できる |
| **M5** 単一スレッド高速化 | MIR 最適化、静的スケジューリング、2 値推論、Cranelift JIT | Icarus 比 ≫ 10 倍 |
| **M6** マルチコア | パーティション並列 (ルックアヘッド同期)、自動分割 + ユーザ指定、評価並列 | 複数サブシステム構成の SoC (例: OpenTitan) でコア数に応じてスケール、出力はシングルスレッドと完全一致 |
| **M7** 検証言語 | class、動的配列/キュー/連想配列、fork/join、mailbox/semaphore、clocking、program、**DPI-C 完全版** (export、時間消費 task) | クラスベースのテストベンチが動く |
| **M8** randomize / coverage / SVA | 制約ソルバ、covergroup、SVA。デバッグ API に `assertion_trace` を追加 | 該当する sv-tests に合格 |
| **M9** UVM / VPI | UVM (1800.2) を無改造で実行、VPI (cocotb) | OpenTitan DV の一部が動作 |
| **M10** 業務 SoC | 互換オプション、インクリメンタルコンパイル、大規模対応のチューニング | 業務 SoC の実テストが通る |

M4 (デバッグ) を高速化より前に置いているのは、状態管理の設計が JIT と並列化の両方に効くため。
デバッグ基盤を先に作ると、後続の開発 (コーパスでの失敗調査) 自体も速くなる。

## 12. 主なリスク

| リスク | 対策 |
|---|---|
| 規格の巨大さ | コーパスの到達段階を可視化し、実際に使われる機能から実装する |
| 4 値・強度で遅くなる | 縮退表現 (強度なし → 4 値 → 2 値) を静的解析で選ぶ |
| 並列化しても同期待ちで速くならない | レジスタ境界のルックアヘッド、プロファイルに基づく分割、ユーザ指定。同期コストを計測して見える化する |
| 決定性の破れ (並列、DPI、OS 依存) | 決定性テスト (スレッド数を変えて結果のハッシュを比較) を CI に入れる。DPI は記録/再生する |
| DPI の時間消費 export task | スタックフルコルーチンで実装する。プラットフォーム依存部分は早めにプロトタイプする |
| 暗号化 IP | 業務 SoC での扱いを早期に確認する (§10.3) |
| 制約ソルバ | 区間伝播/BDD から始め、難しい制約は SAT にフォールバックする |
