## 2. 設計判断 D-1 (4 値を 64 ビットのプレーン分離にし、`svLogicVecVal` とゼロコピーにしない) の評価

### 2.1 比較した代替案
| 案 | 配置 (幅 w、nw = ceil(w/64)) | 長所 | 短所 |
|---|---|---|---|
| **A: 計画 (D-1)** | 値ごとに `[a_0..a_{nw-1}, b_0..b_{nw-1}]` (u64) | 64 ビットのワード並列。4 値の算術を「bval に 1 があれば全 X、無ければ aval プレーンに 2 値カーネル」と書け、2 値カーネルを**そのまま**使える (aval プレーンが連続しているため)。幅 ≤ 64 は `[a, b]` の 16 バイトで JIT が 2 回のロードで扱える。slang の `SVInt` も同じプレーン分離 (下位 nw ワードが値、上位 nw ワードが未知ビット) で、実績のある選択 | DPI の 4 値引数は毎回変換が要る。幅 ≤ 32 の 4 値信号が 16 バイトになる (B の 2 倍) |
| B: `svLogicVecVal` と同一 (u32 で a/b 交互) | `[a0, b0, a1, b1, …]` (u32) | 4 値の DPI 引数がゼロコピー。幅 ≤ 32 は 8 バイトで省メモリ | 33〜64 ビットの値が 2 回のロード + 結合になる (`logic [63:0]` はよくある)。加算の桁上げ・シフト・乗除算が 32 ビット単位になり、多倍長は約 2 倍遅い。2 値カーネルを aval に適用するにはストライド付きのカーネルが別に要る。JIT の式 (§3.4) が全部 32 ビット単位になる |
| C: u64 で a/b をワード単位に交互 | `[a0, b0, a1, b1, …]` (u64) | 幅 ≤ 64 は A と同一。広い値で a_i と b_i が同じキャッシュラインに乗る | `svLogicVecVal` とはやはり一致しない (u32 単位の交互ではない) のでゼロコピーにならない。aval が連続しないので 2 値カーネルの再利用ができず、ストライド付きカーネルが要る。A に対する利点は局所性だけで、幅 > 64 の 4 値演算はどうせ両プレーンを順に読むので差は小さい |
| D: アリーナ全体で aval 領域と bval 領域を分ける (SoA) | 信号 s の a は領域 A、b は領域 B | 2 値推論で bval 領域を丸ごと捨てられる。X が無いことの検査をまとめてできる | 1 つの信号の a と b が別のキャッシュラインになる。今決める必要は無い |

- 計画の `LogicRef { a: &[u64], b: &[u64] }` は「プレーンは隣接していなくてよい」としているので、**A と D はどちらもカーネルを変えずに選べる**。この柔軟性は良い。M5 で D を試す余地が残る。
- C は A に対する利点が小さく、2 値カーネルの共有という A の大きな利点を失う。B は DPI の 4 値引数のためにすべての演算を遅くする。**A (D-1) を支持する。**

### 2.2 DPI 頻繁呼び出し (業務 SoC の擬似メモリ、PLAN §6.1) への影響
- 変換が要るのは **4 値の packed 引数 (`logic [N:0]` → `svLogicVecVal*`) だけ**。
  - `int`/`longint`/`byte`/`shortint`/`bit` スカラ、`chandle`、`string` は値渡しで、配置に関係なく変換は無い。
  - 2 値の packed (`bit [N:0]` → `svBitVecVal*`) は A でもゼロコピー (リトルエンディアンなら u64 列と u32 列は同じバイト列)。
  - 擬似メモリの典型的な形 (`input longint unsigned addr`、`output bit [63:0] data`、`int` の戻り値) は変換ゼロ。`logic [511:0]` のキャッシュライン幅の引数でも 32 ビット単位の詰め替え 16 回で、数 ns の規模。DPI 呼び出しそのもの (間接呼び出し、スコープの設定、output 引数の書き戻しとイベント発火) と比べて小さい。
- **ただし、ゼロコピーにできる場合でも、output/inout 引数をアリーナの信号に直接書かせるのは意味論上できない**。output は関数から戻ったときに実引数へ代入される (代入でイベントが起きる、戻らずに `disable` された場合は書かない等) ので、一時バッファが要る。2 値のゼロコピーが効くのは input (const ポインタ) だけで、output は「一時バッファ → 最上位要素のマスク → 代入」になる。この点を §3.2/§3.8 に書くこと (R-20)。
- **4 値の open array で C 側がポインタを直接使う場合** (`svGetArrayPtr` / `svGetArrElemPtr`) は、規格上は「実装の表現」へのポインタで、正規表現 (canonical) との変換は `svGet/PutLogicArrElemVecVal` で行う (Annex I の `svdpi.h` の構成から読み取れる)。とはいえ業務コードが `svGetArrElemPtr` の戻り値を `svLogicVecVal*` にキャストしている可能性はある。ユーザに確認すべき事項 (R-21)。
- 結論: PLAN §3「メモリ表現が一致」・§6.1「引数の変換なし」は 4 値については元々成り立たない記述。STATUS の決定 (D-1 採用、PLAN.md を「エンコーディングが一致、配置は境界で変換」に直す) を支持する。M3 で DPI 呼び出しのベンチマーク (4 値 64/512 ビット引数) を作って変換コストを実測する、という項目を M3 の計画に入れておくこと。

### 2.3 JIT (M5) への影響
- 幅 ≤ 64 で `[a, b]` が隣接しているので、Cranelift から 2 回のロード (または 1 回の 128 ビットロード) で取れる。§3.4 の式は 64 ビットのレジスタ演算に素直に落ちる。B より明らかに有利。
- 懸念は**狭い値のメモリ量**だけ (R-3)。1 ビットの `logic` も 16 バイト、`logic [7:0] mem [0:2**20-1]` が 16 MiB になる (必要量は 2 MiB)。キャッシュ効率とチェックポイントの量に直接効く。

### 2.4 チェックポイント (M4) への影響
- 値がポインタを含まないワード列なので、A でも B でも memcpy / ページ単位の差分で済む。配置の違いはチェックポイントの正しさには影響しない。
- 影響するのは**量**。上の狭い値・狭い要素の配列の膨張がスナップショットの大きさと差分の粒度に効く (R-3)。

### 2.5 判定
D-1 は妥当。条件として、(1) 「配置の契約」の適用範囲を「スカラの変数・ネット (packed 値 1 個)」に限り、unpacked 配列の要素の詰め方は M1/M3 で別に決める余地を残すこと (R-3)、(2) output 引数のゼロコピー不可を明記すること (R-20)、の 2 点を求める。

## 3. 指摘一覧

重要度: **blocker** (このままでは実装できない・後で大きな作り直しになる) / **major** (計画の修正が必要) / **minor** (直すとよい) / **question** (ユーザ・マネージャの判断が要る)。

### blocker

#### R-1 [blocker] workspace の `unsafe_code = "forbid"` だと `tests/no_alloc*.rs` がコンパイルできない
- 該当: §2.2 `[workspace.lints.rust] unsafe_code = "forbid"`、§5.5 (確保回数カウンタのため「`unsafe` を `// SAFETY:` 付きで許可」)、A-3。
- 問題: `[lints]` は統合テストを含むパッケージの全ターゲットに適用される。`forbid` は下位で `allow` できないので、`GlobalAlloc` の `unsafe impl` を持つテストファイルが E0453 で落ちる。rustc 1.97.0 で実際に試した:
  `error[E0453]: allow(unsafe_code) incompatible with previous forbid … forbid lint level was set on command line (-F unsafe_code)`。
  `deny` にすると `#![allow(unsafe_code)]` 付きのテストが通ることも確認した。T3 は着手直後にこれに当たり、L-6 (確保 0 回の検査) が書けない。
- 修正案: workspace は `unsafe_code = "deny"` にする。各 crate の `lib.rs`/`main.rs` に `#![forbid(unsafe_code)]` を書く (§2.1 のとおり)。`no_alloc*.rs` だけ先頭で `#![allow(unsafe_code)]` とし、`// SAFETY:` を付ける。A-3 の文言を「ライブラリと bin のルートが `#![forbid(unsafe_code)]`、`unsafe` があるのは `tests/no_alloc*.rs` だけ」に直す。

### major

#### R-2 [major] 2 値の値に 4 値の自己決定オペランドが来る場合の意味論と API が決まっていない
- 該当: §3.3「2 値と 4 値の混在は sema が型変換を挿入するので、ライブラリ側で混在演算を持つ必要がない」、§3.5 (c)(d)(e)(f) の 2 値版。
- 問題: 文脈決定のオペランドなら、2 値 → 4 値の変換は情報を失わないので、sema が 4 値に揃えればよい。しかし**自己決定のオペランド** (シフト量、べき乗の指数、選択のインデックス、`?:` の条件) は、データ側が 2 値でも 4 値の X/Z を持ちうる。そして結果を決めるのはその X/Z である。例:
  `bit [7:0] b; logic [2:0] s = 3'bx; … b << s` は規格上「シフト量に x → 結果は x」で、2 値の型に入ると 0 になる。sema がシフト量を 2 値に変換すると `s = 0` になって結果は `b` で、違う値になる。
  同様に `bit` の配列/ベクタを X のインデックスで読む (2 値なら 0)、`c ? t : f` で c が X、t/f が 2 値 (ビットが違う所は X → 0)。
  さらに、この式の結果が 2 値なのか 4 値なのか (2 値データに X のシフト量を与えた結果の型) 自体を規格で確認していない。
- 修正案: (1) 2 値カーネルのうち自己決定のオペランドを取るもの (`shl2/shr2/ashr2`、`pow2` の指数、`index_value`、2 値版の `cond_merge2`) は、そのオペランドを `LogicRef` で受けられるシグネチャにする (または `Index::Unknown` / `Option` を受ける)。X のときの 2 値の結果 (全 0 にするのか) を表に書く。(2) 「2 値オペランドと 4 値の自己決定オペランドを持つ式の結果の型」を §10.2 の [要確認] に加え、U-7 の VCS 確認の項目に入れる。(3) `cond_merge2` (違うビットは 0) を §3.5(f) に明記する。API の形が M5 の JIT ヘルパと 2 値推論に効くので、M0 のうちに決めること。

#### R-7 [major] §3.6 の幅規則の要約に誤りがある (crate ドキュメントとして M1 の sema が従う表)

- 内容: 使っている場合、D-1 の配置ではその C コードが動かない (実装の表現へのポインタになるため)。open array の要素だけを正規表現 (`svLogicVecVal`) で持つ選択肢を M3 で検討する必要がある。ユーザに確認し、M3 の計画の入力にする。

#### R-22 [minor] STATUS の決定事項と計画本文の不一致
- 該当: §6「サードパーティの action はメジャーバージョンのタグで指定する (SHA 固定にするかは §10 U-5)」。STATUS の決定ログでは U-5 = 「コミット SHA で固定」。
- 修正案: §6 と §10 U-5 を決定に合わせて直す (T2 で SHA 固定)。U-1〜U-7 の決定済みの項目も §10 に「決定」と書き込む。

#### R-23 [minor] アリーナの API の細部
- 該当: §4.4。
- 修正案: (1) `ArenaLayoutBuilder::alloc` は `u32` の溢れを検出する (`Result`、または `checked_add` して panic を明示する)。(2) `content_hash` はワードをリトルエンディアンのバイト列として FNV-1a にかけることを明記する (プラットフォーム非依存の定義にするため)。(3) `WordOffset(u32)` で表せるのは 2^32 ワード = 32 GiB まで、という上限を doc に書く。

#### R-24 [minor] `no_alloc` の検査はスレッドに注意する
- 該当: §5.5。
- 問題: テストハーネスは同じバイナリ内の `#[test]` を並列のスレッドで走らせる。グローバルなカウンタだと、他のテストやハーネス自身の確保を数えてしまう。
- 修正案: カウンタをスレッドローカルにする (`const` 初期化の `thread_local!` は確保しない)、または `no_alloc*.rs` は `#[test]` を 1 つにまとめる。

#### R-25 [minor] `deny.toml` の許可ライセンスを絞る
- 該当: §6 `deny` (MIT, Apache-2.0, Unicode-3.0, Unlicense, BSD-3-Clause, Zlib)。
- 問題: walkdir/globset は「Unlicense OR MIT」なので、MIT を許可していれば cargo-deny の判定は通る。Unlicense を単独で許可する必要は無い。CLAUDE.md の「Apache-2.0/MIT 互換に限る」に照らして、必要なものだけにする。
- 修正案: T1 で `Cargo.lock` が確定した時点の `cargo deny list` の結果から、必要なライセンスだけを許可リストに入れる。

### question

#### R-26 [question] 幅 ≤ 32 の 4 値を u64 1 個 (下位 32 ビット = a、上位 32 ビット = b) に詰める案を M5 で検討する余地を残すか
- 内容: この配置は `svLogicVecVal` の 1 要素とバイト列が一致する。幅 ≤ 32 の 4 値の DPI 引数がゼロコピーになり、狭い信号のメモリも半分になる。一方、JIT の式は幅で 2 通りになる。M0 で採る必要は無い。ただし、層 1 の仕様を「レジスタ上の `L64 {a, b}` の演算」と「メモリからのロード/ストア」に分けて書いておけば、M5 で記憶域の配置だけを変えられる。§3.4 に「層 1 は値に対する演算で、記憶域の配置とは独立」と一文入れることを勧める (R-3 と同じ考え方)。

#### R-27 [question] `MAX_WIDTH = 2^24` で良いか
- 内容: Verilator の既定の上限は 65536 ビットで、それより大きいとエラーにしている (`--max-num-width`、6.9.1)。2^24 でも内部の型 (`u32` の幅、`i64` のオフセット) は問題ない。ただし proptest は 1024 ビットまでで、2^24 ビット近くでの動作 (10 進表示が O(n^2)) は確認されない。上限近くの幅のスモークテストを 1 つ入れるか、上限を 2^20 程度に下げるかを決めるとよい。U-6 の判断材料として記録する。

## 4. タスク分解の評価 (重点 3)

- 変更範囲の分け方 (ファイル単位で担当を分け、`lib.rs`/`ops/mod.rs` は T3 が先に宣言し、`impl LogicVec` を演算ファイルごとに分ける) は良い。マージで衝突しない設計になっている。`no_alloc_<area>.rs` と `proptest-regressions/` もファイル名で分かれるので衝突しない。
- 依存関係は概ね正しい。T13 → T12, T2、T11 → T3 も妥当。T7/T8 が T5 の多倍長除算に依存しないように `words.rs` を T3 に置いたのも良い。
- 回らない、または詰まる恐れがあるのは次の 4 点。
  1. T3 の律速 (R-5)。T3a/T3b に分ければ、T4/T6 は早く着手できる。
  2. 参照モデルの独立性 (R-4)。T9 として分ければ波 2 の並列度も上がる (T2, T3a, T9, T10, T12)。
  3. worktree の運用 (R-6)。「波ごとにコミットしてから次の worktree を作る」を明記しないと、波 3 の worktree に T3 の成果が無い。
  4. R-1 (lint) で T3 の完了条件が満たせない。
- 推奨する波:
  ```
  波 1: T1
  波 2: T2  T3a  T9(参照モデル)  T10  T12
  波 2.5: T3b                    (T3a のコミット後。T4/T6 と並列可)
  波 3: T4  T6  T11  T13          (T3a のコミット後)
  波 4: T5  T7  T8                (T3b, T9 のコミット後)
  ```
  同時に走る worktree は最大 4〜5 本になり、ビルドの負荷も分散する。
- 完了条件はおおむね検証可能 (コマンドの成否、件数、ハッシュの一致)。L-1 の「§3.5 の表のすべての演算」は、テスト計画で演算ごとのチェックリストに展開すること。K-2 の 1028 件と 79 件は実ファイルで確認した。

## 5. 過剰設計の評価 (重点 4)

全体としては抑制が効いている。JIT ヘルパ、差分スナップショット、並列インターンは M4 以降に回してあり、M0 で作るのは後続がすぐ使うものに絞られている。軽くできる余地があるのは次の点 (どれも minor。直すかどうかはマネージャ判断)。
- **コーパスの `glob` アダプタ、`--jobs N`、`summary.md`、`path =` のローカルソース、`corpus/private/*.toml`**: M0 では全ケースが `NotImplemented` で、これらの機能を使う場面が無い。M0 は「sv-tests アダプタ + `run` の JSONL 出力」に絞り、残りは使い始める M1 (並列実行はパースが入ってから) と M3 (CPU コアの glob) に回すと、T13 が S〜M に縮む。ただしマニフェストの形式 (`kind` で分ける形) は今のままにして、後から足せるようにしておくのが良い。
- **診断の人間向け表示**: 複数行の span、色、fix-it の表示まで M0 でゴールデンテストを作るのは早い。パーサが無いので、実際の表示要求が分からないまま形を決めることになる。M0 は JSON (AI 向けで、スキーマの版管理が要るもの) と、単一行の span の人間向け表示だけにし、複数行・色は M1 で入れてもよい。
- **3 層 × `_assign` 版 × 2 値版の全組合せの差分テスト**は量が多いが、M5 の JIT の正しさの土台になるので過剰ではない。残すべき。
- `FileOrigin::Include/MacroExpansion` の列挙子だけ先に用意するのは、コストがほぼゼロなので問題ない。

## 6. 性能面
- 4 値の算術を「X 検査 → 2 値カーネル」にし、幅 ≤ 64 をインライン、`Scratch` を呼び出し側が持つ設計は、ホットループでヒープ確保をしないという PLAN §9 の方針に合っている。
- 明らかに遅くなる設計は無い。気になるのは狭い値と配列のメモリ量 (R-3) だけ。10 進表示・Knuth D の O(n^2) は計画どおり後で直せばよい。
